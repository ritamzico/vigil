# WAL Recovery Performance vs. Baseline (No WAL)

**Treatment:** `feature/wal` (WAL + periodic snapshots) · **Control:** `main` (no persistence, re-reads from line 0).
**Dependent variable:** recovery time = wall-clock from a fresh daemon start to "ready" (index fully loaded and queryable), detected by polling `vigil "| count"` until it equals the ingested line count.

> **TL;DR.** WAL recovery is **consistently and significantly faster** than the no-WAL baseline for medium/large logs. After a graceful `--stop`, recovery is **~1.6–1.8× faster** from 100K lines up — e.g. **1.59× at 1M lines** (1.43 s vs 2.27 s). After a hard `kill -9`, the win is more modest (**~1.1×**, rising to **1.35× at 1M**) because the un-checkpointed WAL tail still has to be replayed. Below ~10K lines the two are **statistically indistinguishable** — recovery there is dominated by a ~20 ms fixed startup floor. **Full matrix completed: 600/600 runs, all 30 cells measured.**
>
> This is a **re-run after fixing two WAL bugs** the first benchmark uncovered (the 4 MiB snapshot serialization cap and a checkpoint failure that crashed the daemon at 1M). The graceful-recovery speedup roughly **tripled** (≈1.1× → ≈1.7×) once the snapshot actually serializes — see §5 for the before/after.

## 2. Methodology

Per trial (`scripts/bench.py`):

1. Wipe `/tmp/vigil.sock` and the data dir (fresh — no pre-existing snapshot/WAL).
2. **Ingest:** start daemon, wait until `| count` == expected (builds index + WAL).
3. **Settle** 0.5 s so the WAL tail is durably fsync'd (and any periodic checkpoint can land).
4. **Interrupt** — one of:
   - `stop` → `vigil --stop` (graceful; forces a final checkpoint covering everything ingested).
   - `kill` → `kill -9` (hard crash; only the last *periodic* checkpoint, every 2 s, is durable).
5. **Recovery (measured):** restart daemon, time until `| count` == expected again.
6. Teardown + wipe.

**Interruption types.** vigil installs **no SIGTERM/SIGINT handler**, so a bare `kill -TERM` would be identical to `kill -9` (no final checkpoint). The meaningful axis is therefore **`vigil --stop` (graceful, forces a final checkpoint) vs. `kill -9` (crash)** — the two genuinely different recovery paths. This replaces the spec's SIGTERM/SIGKILL split.

**"Interruption %".** Made deterministic by writing `N × pct` lines and letting the daemon fully ingest them, rather than racing to kill mid-ingest. Recovery cost depends on the *absolute* number of ingested events, so `pct` and `size` are partially redundant (e.g. 1M@10% ≈ 100K@100%) — visible in the results.

**Measurement floor.** Readiness is polled with one-shot `vigil "| count"` processes (~20 ms spawn cost). This adds an identical fixed offset to **both** branches, so the WAL−noWAL *difference* (what the t-test evaluates) is unbiased; it only inflates p-values for the smallest cells.

**Matrix:** 5 sizes (1K/10K/100K/500K/1M) × 3 pcts (10/50/100) × 2 types × 2 branches × 10 trials = **600 runs, all completed** (the 1M cell no longer crashes — see §5).

## 5. Bugs found and fixed

The first benchmark run uncovered **two real defects in the WAL feature**. Both have since been fixed; this report is the re-run on the fixed binary.

### 5.1 Snapshot serialization failed above ~47K events (root cause)

`Snapshot::save` called `wincode::serialize(self)`, which enforces a **4 MiB preallocation cap** on encoded sequence length (an OOM guard meant for *untrusted* input). Encoded snapshots cost ~88 bytes/event, so above ~47K events serialization errored with `Encoded sequence length exceeded preallocation limit of 4194304 bytes`, **no `snapshot.bin` was ever written**, and recovery for every log ≥ 100K silently fell back to WAL replay alone — defeating the snapshot's whole purpose.

**Fix:** `save`/`load` now use `wincode::config::{serialize,deserialize}` with `Configuration::default().disable_preallocation_size_limit()`. The snapshot is vigil's own trusted output, so the cap adds no safety; the wire format is unchanged. Covered by a new 100K-event round-trip regression test.

### 5.2 Periodic-checkpoint failure crashed the daemon

When 5.1 fired inside the *periodic* checkpoint task, the daemon treated it as fatal and called `std::process::exit(1)`, dying mid-ingest. This is why **1M@100% was unmeasurable** in the first run (large enough for a checkpoint tick to fire during ingest).

**Fix:** the checkpoint-task error arm now logs and **respawns** the task instead of exiting — a failed checkpoint can no longer take down a daemon whose index is still queryable and whose WAL still holds the data.

### Before / after (100% ingested, speedup = no-WAL / WAL)

| size | type | before fix | after fix |
|---|---|---|---|
| 100,000 | stop | 1.13× | **1.74×** |
| 500,000 | stop | 1.10× | **1.61×** |
| 1,000,000 | stop | *crashed* | **1.59×** |
| 100,000 | kill | 1.06× | 1.12× |
| 500,000 | kill | 1.12× | 1.12× |
| 1,000,000 | kill | *crashed* | **1.35×** |

The graceful-recovery speedup roughly **tripled** for large logs, and the 1M cell that previously crashed now completes and posts the largest absolute savings in the study.

## 6. Interpretation

**Where does WAL help most?** Graceful `--stop` recovery on any log ≥ 100K lines, where a full final snapshot means restart is *load snapshot* rather than *re-parse every line*: a steady **~1.6–1.8×** across 100K–1M, worth **~93 ms at 100K**, **~409 ms at 500K**, and **~842 ms at 1M** per recovery. This is the size-independent win a snapshot is supposed to deliver, and it only appeared once §5.1 was fixed.

**Why is `kill` weaker than `stop`?** After a hard crash only the last *periodic* checkpoint (every 2 s) is durable, so recovery = load that snapshot **+ replay the WAL tail** written since. Small logs finish ingesting before the first checkpoint tick, so on crash there's little/no snapshot and recovery is mostly WAL replay → only ~1.1×. At 1M, ingest runs long enough that several checkpoints land, so a large prefix is snapshotted and only the tail is replayed → **1.35×**. That `stop` ≫ `kill` gap is itself confirmation the snapshot now works (in the first run they were nearly equal because *neither* produced a usable snapshot).

**Is there a break-even size?** Yes — around **~10K lines**. Below it, recovery is dominated by the ~20 ms fixed startup/poll floor; WAL and no-WAL are statistically indistinguishable (all 1K cells, and most 10K cells, inconclusive). For pure **recovery-speed** purposes on tiny logs the WAL overhead isn't worth it — though it still buys crash-durability semantics the baseline lacks (a separate axis from speed).

**Scaling.** Both branches are O(n) in lines. WAL replay (~0.97 µs/event) is a smaller constant than JSON re-parse (~1.09 µs/event), which alone gives the ~1.1× `kill` win; the working snapshot is what lifts graceful recovery to ~1.6× by replacing most of that linear work with a single bulk load.

**Bottom line.** The WAL feature now delivers a **large, statistically robust recovery speedup** — ~1.6–1.8× on graceful restart for any non-trivial log, up to ~840 ms saved at 1M — with both previously-discovered defects fixed and the full matrix completing cleanly.
